Definitions

Persistent ID
A stable identifier for the same entity across all its versions. For example, dodgeball.annotate-throw identifies the task of identifying the players, positions, and outcome of a marked throw. The case keeps that ID when its grading rule changes. Retired IDs stay reserved.
Version
A fixed snapshot of an entity at a particular point in its history. For cases and prompt templates, the framework uses the full Git commit SHA as the version identifier. For example, dodgeball.annotate-throw at 8f3c2a1… (an illustrative, abbreviated SHA) refers to the case as defined at that commit. If a later commit corrects its grading rule, the case keeps its persistent ID and the new SHA identifies the updated version.
Case
A versioned definition of the public task instructions, public response schema, fixtures, and private answer key.
Fixtures
The inputs and setup a case requires before an attempt begins. For the dodgeball case, the engine places the pinned clip, roster, and court overlay at the paths named in the task.
Task
The public case field that tells the subject what to do.
Response schema
The public case field that defines the JSON object the subject must return.
Prompt template
Versioned wording with a {{task}} placeholder. The engine fills it with the case’s task instructions and JSON response schema to produce the delivered prompt.
Delivered prompt
The exact user message or conversation the evaluation engine sends to the subject after rendering the task instructions and response schema in the selected template.
Subject
The tool-using agent being evaluated.
Agent configuration
The provider, model, harness, and reasoning effort selected for the subject. Pi is the default harness. Harness configuration includes the selected extensions and their versions.
Attempt
One execution of a subject on one case using one selected prompt template version. Each attempt starts fresh with the case’s fixtures. Each fresh attempt under the same conditions counts as one replication, including the first. Replications use the same case and prompt template versions, fixtures, agent configuration, tool permissions, and budgets.
Run
A collection of attempts for a specified suite version, agent configuration, and selection of cases. The run setting replications per case specifies how many fresh attempts to schedule for each selected case under each selected prompt template.
Suite
A named collection of cases. Each published suite version pins the case and prompt template versions it includes.

A new suite release can pin the corrected case version while earlier attempts still point to the version they used.

Harness extensions

Pi extensions run in the harness process and can register model-callable tools with pi.registerTool(). The executor applies the attempt’s permissions to the harness and its extensions. Pi extension documentation

For example, a dodgeball extension could expose inspect_frame. A local implementation reads the staged clip with FFmpeg inside the attempt. If FFmpeg needs installing, its download goes through the package proxy in the same way as any other software download. A hosted implementation can send the same tool call to the external tool broker, which scopes the request to the attempt’s clip and records the outcome. The Pi trace identifies the model’s request. The executor or broker supplies independent evidence of its effects.

An optional adapter must expose the same domain tools through its own harness’s mechanism, and a comparison across harnesses records any difference in the tools exposed.

Assembling an attempt

  1. Prepare fixtures. The engine provisions a fresh isolated environment from the selected case, stages its pinned fixtures, and verifies both the effective access policy and the subject’s ability to read the paths named in the public task.
  2. Render the prompt. The engine replaces the selected template’s {{task}} placeholder with the task instructions followed by the response_schema from the same case version. The engine passes that same schema directly to the validator. The private answer key goes to the answer grader.
  3. Launch the agent. Once the fixtures are ready, the engine launches the harness with native session persistence enabled. At launch, it stores the exact prompt sent under the attempt ID, alongside the case, template, and fixture references.

Domain-specific fixtures, tools, and graders plug into these contracts. A domain author should be able to add a case without changing the engine. Adding an adapter for another harness leaves cases, prompt templates, graders, and stored records unchanged.

Generating and validating cases

  1. Choose a case. Record the capability it tests and the source of the example.
  2. Draft the case. Fill in the case contract and specify any acceptable alternative answers.
  3. Promote the case. An agent typically drafts the case. A person checks the answer key against the reference evidence, then promotes it. Record who promoted it and when. A run includes only promoted case versions. Every new version starts as a draft.
  4. Recheck live fixtures. For cases that use live data, specify when to revalidate the answer key. If the expected answer changes, create a new case version.

JSON submission

Every MVP attempt requires one JSON object as the entire final response. The delivered prompt contains the case’s response schema. The engine preserves the raw final reply. A missing reply, Markdown fence, surrounding prose, malformed JSON, or schema violation fails the submission. Validate required keys and types before comparing values. A string such as "12" fails a field declared as an integer.

Answer-key rules

The answer key is a set of checks. Each check names the submitted value it covers, its private expected value, an error measure, and a nonnegative tolerance. The covered value is one field, an array field, or a group of fields that together form one quantity, such as a point. An error measure is a deterministic function of the submitted and expected values that returns one nonnegative number in declared units. A check passes when the error is at most the tolerance. Every required field belongs to at least one check. Exact matching is the default.

  • Exact. The submitted value equals the expected value. Use this for player IDs, outcome labels, and numbers that must match exactly.
  • Absolute difference. For one number, the error is the absolute difference between the submitted and expected values in the field’s units. An expected value of 40 with a tolerance of 2 accepts 38 through 42.
  • Relative difference. For one number, the error is the absolute difference as a percentage of the magnitude of the expected value. An expected value of 40 with a tolerance of 2% accepts 39.2 through 40.8. At an expected value of zero, only zero qualifies. Use an absolute difference if nearby values should pass. For rates, specify whether an allowance is in percentage points or relative percent.
  • Distance. For numeric vectors of equal length whose components share one unit, the error is the Euclidean distance between the submitted and expected vectors. An expected point of (4.2, 8.4) with a tolerance of 1 accepts any point within 1 unit of it.

A case may declare another error measure if it is deterministic, defined in the case version, and named in the grade. The answer grade records each check’s error and tolerance, so a regrade under a different tolerance needs no new attempt.

Automatic pass or fail

  • Answer. Pass when the JSON satisfies the schema, every answer-key check passes, and archived files or independently observed effects confirm any required deliverables or actions.
  • Integrity. The session grader checks the transcript against trusted execution records. Pass when evidence covers every rule throughout the attempt. Fail on a confirmed violation and cite the rule and event. A blocked request fails only if the rule forbids making it. If evidence is incomplete and no violation is established, leave integrity unscored.
  • Overall. Both verdicts must pass. Either failure makes the attempt fail. Otherwise, an unresolved verdict leaves the attempt unscored. Preserve both results and their evidence.

Installation review

The session grader reviews successful installs against the framework’s integrity rules and the observed use of each library. An ordinary video decoder is expected for the dodgeball case. Evidence that an installed package supplied precomputed labels for the marked clip warrants a suspicious-installation flag. Record the package, reason, relevant rule, and supporting event IDs. A flag prompts review. Fail integrity only when trusted evidence establishes a prohibited action, such as reading restricted labels. A package name alone cannot establish that action.

Isolation and integrity

The agent may choose its methods and install and use tools within the isolated environment. Across all cases, accessing private answers, tampering with evaluation evidence, or escaping the container violates integrity. Give each attempt a fresh workspace, clean session, explicit environment, and declared fixtures. State persists across turns within that attempt. Keep service credentials, private answer keys, graders, proxies, evidence stores, and sibling workspaces outside the subject’s control.

Separate the harness’s model connection from tool network access. Enforce scoped service access and required broker routes for every process in the attempt. Test each executor with disposable fixtures for restricted files, undeclared services, and prior workspaces. An unenforceable policy invalidates the attempt. Claims about unseen tasks also require held-out evaluation material.

Project storage

Each evaluation project has one evaluations.sqlite database shared across runs. The engine owns the database and the adjacent artifacts/ directory. Both live outside the agent’s workspace. The dashboard reads the same database for comparisons and drill-down.

Writing and reviewing attempts

Create the attempt row before launch. On completion, timeout, or cancellation, archive the available native transcript before teardown and link it to the attempt. Store the final response if present, terminal execution status, and any missing or partial evidence. The engine coordinates writes across concurrent attempts. The session grader reads the archive after execution.

Append each grading result with its own grade ID. A regrade adds a row against the same captured evidence. For each reported overall verdict, retain the answer and session grade IDs used to compute it. Count distinct scored attempts when computing sample size and pass rate. Regrading the same dodgeball clip execution changes the available assessments while its contribution to the sample stays at one.

Session and resource record

Link records by attempt ID using the project storage schema. Preserve partial evidence on timeout or cancellation.

  • Manifest. Pin case and template IDs independently to GitHub file permalinks with full commit SHAs. Record fixture identities, budgets, effective permissions, software and context versions, extensions, exposed tools, and requested and resolved model and effort. Include the session grader’s model, instructions version, and settings.
  • Session transcript. Preserve visible messages and tool calls and results in their original order, including turn and call IDs when available. Record any missing coverage, such as a chat-only transcript, and any redactions. Exclude credentials and private reasoning. Retain independent executor or broker records for required effects and access checks.
  • Installations. Record the base image digest and the effective package-proxy policy (pass-through by default). Before teardown, reconcile install requests and outcomes visible in the transcript with the final package inventory and package-proxy download records and any independent installer records. Record installed libraries and dependencies, versions, sources, and artifact digests where observable. Distinguish preinstalled packages, downloads, successful installs, and failed attempts. Mark gaps in coverage.
  • Usage and cost. Preserve native input, output, and cache counters at their reported scope, including whether input totals include cached tokens. Leave missing values unknown. Separate subject and grader usage, wall time, and tool resources. Label costs as provider-reported or estimated and retain the pricing basis.
  • Results. Keep the raw reply, parsed JSON when valid, answer-key checks, answer and integrity verdicts, and availability and suspicious-installation flags with their evidence. A regrade uses the archived evidence. A rerun creates a fresh attempt.

Comparisons and human review

Predeclare cases, replications, budgets, and the primary metric. Compare agents on the same case versions, templates, and fixtures. Record the baseline agent’s permissions and differences in tools, context, or limits. To test wording, vary only the template.

Report results per case, template, and agent configuration. Show scheduled and scored attempts, passes, unscored reasons, elapsed time, and token usage. For example, 20 scheduled attempts with two infrastructure errors and 17 passes yield 17/18 scored attempts passed (94.4%). Link retries to their originals. Label smoke runs and compare suite scores only across compatible coverage.

Summarize tool flags by tool, reason, affected attempts, and recovery. Link findings to evidence. Reviewers can label subject errors, infrastructure problems, and grading defects while preserving the original verdict and any regrade.

Dodgeball stat tracker

The engine stages the marked throw at clip.mp4, the jersey-to-player mapping at roster.json, and the court overlay at court.png in a fresh workspace. The public task names those paths and asks, “Who threw the ball, who was the intended target, what happened, and where was the thrower at release and the target at arrival?” The separate response_schema field defines the player IDs, outcome label, and positions.

For a template reading “Annotate the highlighted play for the stat tracker. {{task}}”, the engine inserts the task instructions and then the response schema after the opening sentence. It verifies that the three files are readable, then launches the agent with the rendered prompt. The subject can then inspect the release and arrival frames for positions and follow the ball through the clip for the outcome.

If the agent tries to install FFmpeg and the requested release is unavailable from the requested source, the session grader flags FFmpeg and links the failed request. If the agent completes the annotation using another video tool, the FFmpeg flag remains visible alongside the answer and integrity verdicts.

Public response schema

For this illustrative fixture, the schema requires six fields and allows no others. event is the constant throw. thrower and target are roster ID strings. outcome accepts hit, miss, catch, or block. thrower_position and target_position are each an array of two numbers, x then y. On a miss, the target is the player the throw was aimed at.

Positions are court metres on the 9 m by 18 m court and locate the midpoint between the player’s feet. The thrower’s position is taken at ball release. The target’s is taken at the ball’s arrival, or at its closest approach on a miss. On the overhead overlay, the top-left corner is (0, 0), x increases to the right across the court’s width, and y increases downward along its length.

Example final response

{
  "event": "throw",
  "thrower": "p03",
  "target": "p11",
  "outcome": "miss",
  "thrower_position": [3.0, 6.9],
  "target_position": [6.5, 11.4]
}

Private answer key

In this example, the reviewer annotated p03 at (2.4, 6.2) in the release frame and p11 at (6.7, 11.2) at the ball’s closest approach, and labeled the outcome miss. The answer grader checks the event, both IDs, and the outcome exactly. Each position array has a distance check with a tolerance of 1 metre.

The response above passes the answer checks. The thrower’s reported position is about 0.92 m from the annotated one, and the target’s is about 0.28 m. Changing only the thrower’s x to 3.2 puts that position about 1.06 m away, which produces a schema-valid response that fails the answer key. Returning "3.0" for that coordinate instead fails schema validation before the position comparison.

If trusted records show that the agent read the private answer key, the session grader returns a failing integrity verdict even when every submitted value is correct.
