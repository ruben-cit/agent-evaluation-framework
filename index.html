Harness extensions

Pi extensions run in the harness process and can register model-callable tools with pi.registerTool(). The sandbox applies the trial’s permissions to the harness and its extensions. Pi extension documentation

For example, a dodgeball extension could expose inspect_frame. Its implementation reads the staged clip with FFmpeg inside the trial.

An optional adapter must expose the same domain tools through its own harness’s mechanism, and a comparison across harnesses records any difference in the tools exposed.

Assembling a trial

  1. Prepare fixtures. The engine provisions a fresh sandbox from the selected task, stages its fixtures, and verifies both the effective access policy and the subject’s ability to read the paths named in the instructions.
  2. Render the prompt. The engine replaces the selected template’s {{task}} placeholder with the instructions followed by the response_schema from the same task version. The engine passes that same schema directly to the answer grader. The private answer key goes to the answer grader.
  3. Launch the subject. Once the fixtures are ready, the engine launches the harness with native session persistence enabled. At launch, it stores the delivered prompt under the trial ID, alongside the task and template references.

Domain-specific fixtures, tools, and graders plug into these contracts. A domain author should be able to add a task without changing the engine. Adding an adapter for another harness leaves tasks, prompt templates, graders, and stored records unchanged.

Generating and validating tasks

  1. Choose a task. Record the capability it tests and the source of the example.
  2. Draft the task. Fill in the task contract and specify any acceptable alternative answers.
  3. Publish the task version. An agent typically drafts the task. An approver checks that the draft makes sense and that its answer key matches its source material, then publishes it. Record who published it and when. A job includes only published task versions. Every new version starts as a draft.

JSON submission

Every MVP trial requires one JSON object as the entire final response. The delivered prompt contains the task’s response schema. The engine preserves the final response as received. With a missing final response, Markdown fence, surrounding prose, or malformed JSON, there is no submission. A schema violation makes the submission invalid. Either outcome is a fail. Validate required keys and types before comparing values. A string such as "12" fails a field declared as an integer.

Answer-key rules

The answer key is a set of checks. Each check names the submitted value it covers, its private expected value, an error measure, and a nonnegative tolerance. The covered value is one field, an array field, or a group of fields that together form one quantity, such as a point. An error measure is a deterministic function of the submitted and expected values that returns one nonnegative number in declared units. A check passes when the error is at most the tolerance. Every required field belongs to at least one check. Exact matching is the default.

  • Exact. The submitted value equals the expected value. Use this for player IDs, outcome labels, and numbers that must match exactly.
  • Absolute difference. For one number, the error is the absolute difference between the submitted and expected values in the field’s units. An expected value of 40 with a tolerance of 2 accepts 38 through 42.
  • Relative difference. For one number, the error is the absolute difference as a percentage of the magnitude of the expected value. An expected value of 40 with a tolerance of 2% accepts 39.2 through 40.8. At an expected value of zero, only zero qualifies. Use an absolute difference if nearby values should pass. For rates, specify whether an allowance is in percentage points or relative percent.
  • Distance. For numeric vectors of equal length whose components share one unit, the error is the Euclidean distance between the submitted and expected vectors. An expected point of (4.2, 8.4) with a tolerance of 1 accepts any point within 1 unit of it.

A task may declare another error measure if it is deterministic, defined in the task version, and named in the grade. The grade records each check’s error, tolerance, and result.

Automatic pass or fail

Pass when the submission satisfies the response schema and every answer-key check passes. Otherwise fail. A trial that ends in an infrastructure failure stays ungraded.

Isolation

The subject may choose its methods and install and use tools within the sandbox. The sandbox must prevent the subject from accessing private answers, tampering with trial evidence, or escaping it. Give each trial a fresh workspace, clean session, explicit environment, and declared fixtures. State persists across turns within that trial. Keep service credentials, private answer keys, graders, the project database and artifact directory, and sibling workspaces outside the subject’s control.

Separate the harness’s model connection from tool network access. Enforce scoped service access for every process in the trial. Test each sandbox against restricted files, undeclared services, and prior workspaces. A trial whose policy cannot be enforced is an infrastructure failure. Claims about unseen tasks also require held-out evaluation material.

Project storage

Each evaluation project has one evaluations.sqlite database shared across jobs. The engine owns the database and the adjacent artifacts/ directory. Both live outside the subject’s workspace. The dashboard reads the same database for comparisons and drill-down.

Writing trials

Create the trial row before launch. When the trial ends, archive the available session transcript before teardown and link it to the trial. Store the final response if present, terminal execution status, and which parts of the trial evidence are missing or partial. The engine coordinates writes across concurrent trials.

A trial receives one grade unless it ends in an infrastructure failure.

Session and resource record

Link records by trial ID using the project storage schema. Preserve partial trial evidence on infrastructure failure.

  • Manifest. Pin task and template IDs independently to GitHub file permalinks with full commit SHAs. Record effective permissions, the base image digest, software and context versions, extensions, exposed tools, and requested and resolved model and effort.
  • Session transcript. Preserve visible messages and tool calls and results in their original order, including turn and call IDs when available. Record any redactions. Exclude credentials and private reasoning.
  • Usage and cost. Preserve native input, output, and cache counters at their reported scope, including whether input totals include cached tokens. Leave missing values unknown. Record wall time and tool resources alongside token usage. Label costs as provider-reported or estimated and retain the pricing basis.
  • Results. Keep the final response, the submission when there is one, and the grade.

Comparisons

Predeclare tasks, trials, and the primary metric. Compare subjects on the same task versions and templates. Record the baseline subject’s permissions and differences in tools, context, or limits. To test wording, vary only the template.

Report results per task, template, and subject configuration. Show scheduled and graded trials, passes, the cause of each ungraded trial, elapsed time, and token usage. For example, 20 scheduled trials with two infrastructure failures and 17 passes yield 17/18 graded trials passed (94.4%). Label smoke jobs and compare pass rates only across jobs that ran the same task and template versions.

Dodgeball stat tracker

The engine stages the marked throw at clip.mp4, the jersey-to-player mapping at roster.json, and the court overlay at court.png in a fresh workspace. The instructions name those paths and ask, “Who threw the ball, who was the intended target, what happened, and where was the thrower at release and the target at arrival?” The separate response_schema field defines the player IDs, outcome label, and positions.

For a template reading “Annotate the highlighted play for the stat tracker. {{task}}”, the engine inserts the instructions and then the response schema after the opening sentence. It verifies that the three files are readable, then launches the subject with the delivered prompt. The subject can then inspect the release and arrival frames for positions and follow the ball through the clip for the outcome.

Response schema

For this illustrative task, the schema requires six fields and allows no others. event is the constant throw. thrower and target are roster ID strings. outcome accepts hit, miss, catch, or block. thrower_position and target_position are each an array of two numbers, x then y. On a miss, the target is the player the throw was aimed at.

Positions are court metres on the 9 m by 18 m court and locate the midpoint between the player’s feet. The thrower’s position is taken at ball release. The target’s is taken at the ball’s arrival, or at its closest approach on a miss. On the overhead overlay, the top-left corner is (0, 0), x increases to the right across the court’s width, and y increases downward along its length.

Example final response

{
  "event": "throw",
  "thrower": "p03",
  "target": "p11",
  "outcome": "miss",
  "thrower_position": [3.0, 6.9],
  "target_position": [6.5, 11.4]
}

Private answer key

In this example, the answer key places p03 at (2.4, 6.2) in the release frame and p11 at (6.7, 11.2) at the ball’s closest approach, and labels the outcome miss. The answer grader checks the event, both IDs, and the outcome exactly. Each position array has a distance check with a tolerance of 1 metre.

The response above passes every answer-key check. The thrower’s reported position is about 0.92 m from the expected one, and the target’s is about 0.28 m. Changing only the thrower’s x to 3.2 puts that position about 1.06 m away, which produces a schema-valid response that fails the answer key. Returning "3.0" for that coordinate instead fails schema validation before the position comparison.

Future extensions

The current framework leaves out the following. Each could be added later. The wording in this section has not been checked for consistency with the glossary.

  • Session grader. An agentic grader that reads the session transcript after a trial and returns an integrity grade, with flags for unavailable tools and suspicious installations.
  • Independent observations. Records of what happened in a trial, made by components outside the subject’s control. They would let integrity be checked against more than the session transcript.
  • Package proxy. A component that routes every software download in a trial and records exactly what was served.
  • Tool broker. A component that mediates the subject’s calls to outside services. It would let a task require an action on a service and confirm that the action happened.
  • Output-file checks. Answer-key checks that cover files the subject produced, not only submitted values.
  • Cancellation. Stopping a trial or job before it ends, and a rule for whether a cancelled trial is graded.
  • Regrade. A new grade for an existing trial from its trial evidence, without executing the subject again. It would avoid new trials when an answer key is corrected.
  • Retry. An automatic replacement, within the same job, for a trial lost to an infrastructure failure.
  • Budgets. Limits on the tokens, time, or cost of a trial, and a rule for grading a trial that exhausts them.
  • Incomplete transcripts. A rule for trials whose session transcript is missing entries.
  • Annotations. A person’s recorded note on a trial, such as labelling a subject error, an infrastructure problem, or a grading defect, kept alongside the original grade.
  • Live fixtures. Fixtures drawn from data that changes over time, with a schedule for rechecking the answer key.
  • Follow-up messages. Delivered prompts of more than one message, so the engine can continue a conversation with the subject during a trial.

Glossary

Versioning

Persistent ID
A stable identifier for the same entity across all its versions. For example, dodgeball.annotate-throw identifies the task that asks for the players, positions, and outcome of a marked throw. The task keeps that ID when its answer key changes. Retired IDs stay reserved.
Version
A fixed snapshot of an entity at a particular point in its history. For tasks and prompt templates, the framework uses the full Git commit SHA as the version identifier. For example, dodgeball.annotate-throw at 8f3c2a1… (an illustrative, abbreviated SHA) refers to the task as defined at that commit. If a later commit corrects its answer key, the task keeps its persistent ID and the new SHA identifies the updated version.

Task

Task
A versioned definition of the instructions, response schema, fixtures, and private answer key. The subject sees the instructions, response schema, and fixtures. It never sees the answer key.
Fixtures
The fixed inputs and setup a task version requires before a trial begins. Changing a fixture creates a new task version. For the dodgeball task, the engine places the clip, roster, and court overlay at the paths named in the instructions.
Instructions
The task field that tells the subject what to do.
Response schema
The task field that defines the JSON object the subject must return.
Answer key
The task field that holds the checks the answer grader applies to a submission. The subject never sees it.
Draft
A task version that no approver has published. A job cannot include it.
Publication
An approver’s recorded approval of one task version, after which a job can include that version.
Approver
The person who checks that a draft makes sense and that its answer key is correct, then publishes it.

Prompt

Prompt template
Versioned wording with a {{task}} placeholder. The engine fills it with the task’s instructions and JSON response schema to produce the delivered prompt.
Delivered prompt
The exact message the evaluation engine sends to the subject at the start of a trial, after rendering the instructions and response schema in the selected template.

Subject

Model
A language model on its own, apart from the program that runs it.
Harness
The program that runs a model in a loop and exposes tools to it.
Agent
A model running in a harness with tools. The framework contains more than one agent: the subject, and usually whatever drafts a task. Each is called by its role, and “agent” names only the general category.
Subject
The agent being evaluated.
Subject configuration
The provider, model, harness, extensions, and reasoning effort that identify a subject. Two subjects with different extensions are different subjects. Permissions are a condition of a job, not part of the subject configuration.

Trials and jobs

Trial
One execution of a subject on one task using one selected prompt template version. Each trial starts fresh with the task’s fixtures. Repeated trials of a task in a job use the same task and prompt template versions, subject configuration, and tool permissions.
Job
A collection of trials for a specified subject configuration and selection of task versions. The job setting trials per task specifies how many fresh trials to schedule for each selected task under each selected prompt template.

Isolation

Sandbox
The sealed place one trial runs in, which enforces what the subject can reach.
Workspace
The directory inside the sandbox where the fixtures are placed and the subject works.

Trial records

Manifest
The conditions a trial ran under, recorded before it starts: the task and prompt template versions, subject configuration, and permissions.
Trial evidence
What is kept from one trial after its workspace is destroyed: the session transcript, the final response, and any files the subject produced. The answer grader reads only this.
Session transcript
The harness’s own record of the messages, tool calls, and tool results in a trial.
Usage
The resources a trial consumed: tokens, cost, and wall time. It is not trial evidence.

Response

Final response
The exact text of the subject’s last message, kept as received. It can be missing.
Submission
The final response read as a single JSON object. There is no submission when the final response is anything other than exactly one JSON object. A submission that violates the response schema is an invalid submission.

Grading

Check
One rule in an answer key: the submitted value it covers, its private expected value, an error measure, and a tolerance. It passes when the error is at most the tolerance.
Grade
The answer grader’s record for one trial: the verdict, each check’s error, tolerance, and result, and the grader version and settings.
Verdict
The pass or fail result in a grade.
Infrastructure failure
A trial that could not run properly for a reason outside the subject’s doing, such as a provider outage.
Ungraded
Having no grade because the trial ended in an infrastructure failure. Ungraded trials are left out of the pass rate.
Pass rate
Passed trials divided by graded trials.
